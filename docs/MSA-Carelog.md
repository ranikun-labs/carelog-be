## 1. 제품 정의 (What)

**CareLog는 "서비스 관리 주체(Manager)가 관리 대상 고객(Client)의 기록과 일정을 관리하는" 범용 CRM Core 위에, 업종별 화면·기능을 모듈로 얹는 B2B SaaS 플랫폼이다.**

- **네이밍 해석**: Care(고객 케어) + Log(불변 기록) — 물리치료에 국한되지 않는 범용 해석
- **버티컬 우선순위**:
    - 1순위: 물리치료 — Manager(치료사) ↔ Client(환자)
    - 2순위: 임대 — Manager(집주인) ↔ Client(세입자)

### 설계 원칙 (Why)

- **코어 순수성**: 코어 계층에는 도메인 언어("예약", "환자", "월세")가 단 하나도 포함되지 않는다.
- **파생 방식은 2가지뿐**: ① 라벨 교체(코어 화면 재사용) ② 전용 화면/테이블 추가(코어 슬롯 확장). 코어 구조 변경은 금지.
- **백엔드 대칭성**: 백엔드 테이블 구조(코어 + 확장 테이블), 프론트 컴포넌트 구조(코어 컴포넌트 + 도메인 폼)가 동일한 추상화 경계를 공유한다.
- **코드 생존성**: 용어는 문서상 의미뿐 아니라 **코드 레벨 충돌 여부**(Java 예약어, 도메인 이벤트 등)를 기준으로 선정한다.

## 2. 코어 용어 정의 (Ubiquitous Language)

> 표기 규칙: 문서·컴포넌트 전반에서 **`코어 용어(물리치료/임대)`** 형식으로 병기한다.

| 코어 용어          | 정의                                                 | 물리치료     | 임대             | 선정 근거                                                                                          |
|----------------|----------------------------------------------------|----------|----------------|------------------------------------------------------------------------------------------------|
| **Manager**    | 서비스 관리 주체                                          | 치료사·원장   | 집주인·관리인        | 대안 부재(차악). 단, 코드에서 `~Manager` 유틸 접미사와 혼동 방지 — 엔티티보다 Role 기반으로 표현                               |
| **Client**     | 관리 대상 고객                                           | 환자       | 세입자            | ~~Customer~~ 폐기: B2B SaaS 표준에서 Customer = SaaS 구매 사업자. 테넌트 도입 시 충돌 예방 (Salesforce·HubSpot 컨벤션) |
| **Journal**    | 관계에서 발생한 **과거 불변 기록** — append-only, SUPERSEDED 체인 | 진료 일지    | 납부 이력·계약 변경 이력 | ~~Record~~ 폐기: `java.lang.Record` / Kotlin 충돌. 기존 백엔드 Journal 도메인 구현체와 일치 — 비용 제로 승격           |
| **Schedule**   | **미래 예정된 일** — 상태 전이 보유                            | 예약(방문)   | 납부 예정일·계약 만기   | ~~Event~~ 폐기: Outbox 이벤트·도메인 이벤트·메시징 Event와 삼중 충돌                                              |
| **Consent**    | Client의 데이터 처리 동의                                  | 민감정보 동의  | 개인정보 동의        | 유지                                                                                             |
| **Inquiry**    | **Manager가 발화 주체**인 Journal 기반 AI 질의 (RAG)         | 치료 이력 질의 | 납부·계약 질의       | 유지. 단 CS 도메인의 "고객 문의"와 구분 — 발화 주체를 정의에 명시                                                      |
| **Role**       | 코어 고정 직급 3종                                        | §4 참조    | §4 참조          | v0.2 신설 — 코어로 승격                                                                               |
| **Permission** | Role에 부여되는 행위 단위 권한                                | §4 참조    | §4 참조          | v0.2 신설                                                                                        |

### 핵심 데이터 흐름: Schedule → Journal 단방향

```text
Schedule (미래 예정)
  상태: SCHEDULED → OVERDUE → COMPLETED / CANCELLED / DEFAULTED
        │
        ▼ 완료 시 결과 적재
Journal (과거 불변 기록)
  append-only, 수정 = 신규 INSERT + 이전 status=SUPERSEDED
```

- 예약(Schedule) 완료 → 진료 일지(Journal) 작성
- 납부 예정(Schedule) 입금 확인 → 납부 이력(Journal) 적재
- **역방향(Journal → Schedule) 생성은 없다**

### Schedule 상태 머신 (코어 5종)

> v0.1의 4종(DEFAULTED 단일)에서 개편. **노쇼는 즉시 종결이지만 연체는 재진입 가능(늦게라도 내면 완납)** — terminal / non-terminal 상태를 분리하지 않으면 상태 전이 규칙이
> 도메인마다 달라져 코어가 성립하지 않는다.

| 코어 상태       | 성격              | 물리치료    | 임대    |
|-------------|-----------------|---------|-------|
| `SCHEDULED` | 초기              | 예약됨     | 납부 예정 |
| `OVERDUE`   | **중간 (재진입 가능)** | — (미사용) | 연체    |
| `COMPLETED` | 종결 (terminal)   | 방문 완료   | 완납    |
| `CANCELLED` | 종결 (terminal)   | 예약 취소   | 계약 해지 |
| `DEFAULTED` | 종결 (terminal)   | 노쇼      | 미납 확정 |

허용 전이:

```text
SCHEDULED → COMPLETED | CANCELLED | DEFAULTED | OVERDUE
OVERDUE   → COMPLETED | DEFAULTED
(terminal 상태에서의 전이는 금지)
```

## 3. 데이터 전략 — 코어 테이블 + 도메인 확장 테이블 (v0.2 신설)

### 결정: 1:1 확장 테이블 채택, JSONB 최소화

| 전략                            | 판정 | 사유                               |
|-------------------------------|----|----------------------------------|
| JSONB 단일 테이블                  | ❌  | 타입 안정성 상실, DB 제약조건 불가, 쿼리 최적화 한계 |
| EAV (key-value)               | ❌  | 조인 지옥, 안티패턴                      |
| 런타임 폼 빌더                      | ❌  | 노코드 플랫폼 개발 = 스코프 폭발              |
| **코어 테이블 + 도메인 확장 테이블 (1:1)** | ✅  | 타입 안정, 도메인별 제약조건, 코어 쿼리 단순       |

### 구조

```text
journals (코어 — 도메인 무관)
 ├─ id, client_id, manager_id
 ├─ title, occurred_at
 ├─ status (ACTIVE / SUPERSEDED), previous_id
 └─ domain_type (PHYSIO / RENTAL)      ← 디스크리미네이터
      │ 1:1
      ├─ journal_physio_details        ← body_part, symptoms, treatment_type
      └─ journal_rental_details        ← amount, paid_at, payment_method
```

- **"도메인 추가 = 마이그레이션 필요"는 의도된 트레이드오프**: 업종 추가는 어차피 화면·로직 개발이 동반되는 이벤트. 런타임에 업종이 늘어난다는 가정은 본 프로젝트에 없음
- **프론트 대칭 구조**: 코어 C7(Journal 작성)은 "제목 + 본문 + 슬롯"만 알고, `PhysioJournalForm` / `RentalJournalForm`이 컴파일 타임에 슬롯에 장착 (폼 정의를
  DB에 넣지 않음)

- **체인 무결성은 `@Version`(낙관적 락) + `UNIQUE(previous_id)`로 보장** — 동시 개정 시 SUPERSEDED 체인 분기를 DB 레벨에서 차단

### JSONB 허용 기준선 (명문화)

| 판정         | 기준                                     | 예시                                                              |
|------------|----------------------------------------|-----------------------------------------------------------------|
| ✅ JSONB 허용 | **스키마를 사전 정의할 수 없는 진짜 비정형** 데이터        | `clinicalData` (자유 서술, AI 파이프라인 타겟), `personalData` (PII 격리 목적) |
| ❌ JSONB 금지 | 도메인이 필드를 아는 데이터 — "정의 가능한데 귀찮아서 JSONB" | 금액, 부위, 상태값 등 → 타입드 컬럼                                          |

## 4. Role / Permission 2계층 (v0.2 신설)

### 구조: Role은 직급(코어 고정), Permission은 출입증(도메인 커스텀)

| Role (코어 고정 3종) | 물리치료 | 임대      |
|-----------------|------|---------|
| `OWNER`         | 원장   | 집주인     |
| `STAFF`         | 치료사  | 관리인     |
| `ASSISTANT`     | 리셉션  | — (미사용) |

### Permission 매핑 (도메인별 배분표)

| Permission        | OWNER | STAFF   | ASSISTANT |
|-------------------|-------|---------|-----------|
| `client:read`     | ✅     | ✅ (담당만) | ✅ (기본정보만) |
| `client:write`    | ✅     | ✅       | ✅         |
| `journal:read`    | ✅     | ✅ (담당만) | ❌         |
| `journal:write`   | ✅     | ✅       | ❌         |
| `schedule:manage` | ✅     | ✅       | ✅         |
| `inquiry:use`     | ✅     | ✅       | ❌         |
| `stats:read`      | ✅     | ❌       | ❌         |

- **권한 판정은 Role 하드코딩이 아닌 Permission 매핑으로**: "리셉션은 일지 접근 불가"는 `ASSISTANT ↛ journal:read` 매핑 한 줄
- **UI 정책 (코어 규칙으로 승격)**: 권한 없는 기능은 에러가 아니라 **화면/탭 자체 미노출**
- 업종 추가 시 Role enum은 불변, Permission 배분표만 신규 작성

## 5. Auth 아키텍처 — 멀티 비즈니스 서버 대비 (v0.2 신설)

### 목표 구조

```text
                [Auth Server]
                 - 토큰 발급 (issuer)
                 - 계정/크리덴셜 관리
                 - 로그아웃 → 블랙리스트 등록 (소유권 이관)
                 - JWKS 공개키 엔드포인트
                      │ 공개키 배포 (JWKS)
                      ▼
[Spring Cloud Gateway]
 - JWT 서명 검증 (공개키)
 - Redis 블랙리스트 조회
 - aud 클레임 ↔ 라우팅 대상 대조
 - 헤더 주입 (X-User-Id, X-Role, X-Gateway-Secret)
        │
        ├──► [carelog-be]   aud: carelog   ← 현재
        └──► [fintech-be]   aud: fintech   ← 확장 예정
```

### 설계 결정 5개

| # | 항목          | 결정                                                 | 근거                                                                            |
|---|-------------|----------------------------------------------------|-------------------------------------------------------------------------------|
| 1 | 서명 방식       | HS256(대칭) → **RS256(비대칭) + JWKS**                  | 대칭키는 서버 추가마다 시크릿 공유 = 유출 반경 확대. 비대칭은 신규 서버가 **공개키만 받아 검증** — 서버가 늘어도 Auth 무수정 |
| 2 | audience 분리 | 토큰에 `aud` 클레임 명시, Gateway가 라우팅 대상과 대조              | carelog 토큰으로 금융 API를 호출하는 **토큰 전용(轉用) 공격 차단**                                 |
| 3 | 토큰 정책 차등    | 금융 aud 토큰은 **짧은 TTL + step-up 재인증** (결제 승인 직전 재인증) | 페이먼트 도메인 표준 관행                                                                |
| 4 | 블랙리스트 소유권   | carelog-be → **Auth 서버로 이관**                       | 토큰 라이프사이클(발급~폐기)은 발급자 책임. 비즈니스 서버 소유 시 fintech-be 추가마다 로그아웃 로직 중복             |
| 5 | 책임 경계       | **Auth = 인증(신원) / 비즈니스 서버 = 인가(리소스 소유권·Role 해석)**  | Auth가 도메인 Role을 알게 되는 순간 결합 시작. 기존 원칙 유지                                      |

### 계정 모델: 계정–멤버십 분리

```text
Auth DB:      users (신원, 크리덴셜)              ← 서비스 무관
비즈니스 DB:  memberships (user_id, role, ...)    ← 서비스별 소속/역할
```

- "한 사람이 carelog에선 OWNER, 금융에선 일반 사용자" 시나리오 수용
- JWT 페이로드는 `sub`(user_id) + `aud` 최소 구성. 도메인 Role은 각 비즈니스 서버가 memberships에서 해석

### 스코프 경계 (직접 구현 vs 미구현)

| 직접 구현 (포트폴리오 스윗스팟)                        | 구현 안 함                              |
|-------------------------------------------|-------------------------------------|
| issuer, JWKS 엔드포인트, 키 로테이션, aud 검증, 블랙리스트 | 풀 OIDC Provider (동의 화면, 소셜 페더레이션 등) |

> 예상 질문 대응: "왜 Keycloak 안 쓰고 직접 구현했나" → 토큰 라이프사이클과 키 로테이션을 직접 다루는 학습 목적. 프로덕션 규모라면 Spring Authorization Server 또는
> Keycloak 채택이 정답임을 인지.

### 금융(fintech) 서버 추가 시 체크리스트

- [ ] `aud: fintech` 토큰 발급 정책 추가 (Auth 설정)
- [ ] Gateway 라우팅 + aud 대조 규칙 추가
- [ ] fintech-be에 JWKS 공개키 검증 필터 장착 (코드 공유 불필요)
- [ ] 짧은 TTL + step-up 재인증 정책 적용
- [ ] memberships 테이블 fintech 스키마 정의
- **Auth 서버 코드 수정: 없음** ← 이 설계의 존재 이유

| C4  | Client 상세    | 3탭 골격: `정보 / Journal / Schedule`                | 탭별 도메인 컴포넌트 주입 가능           |
| C5  | Client 등록·수정 | 기본정보 폼 + **Consent 체크 UI**                      | Consent 미동의 시 저장 차단         |
| C6  | Journal 타임라인 | **SUPERSEDED 체인 뷰** — 최신본 상단, 이전 버전 접기          | 수정 이력 전체 추적, 삭제 불가 표시       |
| C7  | Journal 작성   | 공통 골격: 제목 + 본문 + **도메인 필드 슬롯** (확장 테이블과 1:1 대칭) | 슬롯에 도메인 전용 폼 장착 가능          |
| C8  | Schedule 뷰   | 상태 뱃지 5종. **뷰 컴포넌트는 도메인 분기** (코어는 상태 모델만 제공)    | 상태 전이 액션 (허용 전이만 노출)        |
| C9  | Inquiry 채팅   | SSE 스트리밍 말풍선 + **출처 카드**(Journal ID·날짜) + 👍/👎 | 첫 토큰 1~2초 내, 근거 없으면 "확인 불가" |
| C10 | 설정·알림        | 알림 목록, 로그아웃(→Auth 블랙리스트). 알림 타입은 도메인 확장         | 도메인 알림 타입 플러그인 구조           |

### 코어 공통 컴포넌트 (디자인 시스템 단위)

| 컴포넌트              | 사용처        | 비고                            |
|-------------------|------------|-------------------------------|
| `ClientCard`      | C3, C2 위젯  | 이름 / 최근 활동일 / 담당 Manager      |
| `JournalTimeline` | C4, C6     | SUPERSEDED 체인 시각화             |
| `ScheduleBadge`   | C2, C4, C8 | 상태 5종 컬러 시스템 (OVERDUE는 경고 컬러) |

### 디자인 토큰 정책

- **구조·뉴트럴 컬러·타이포**: 코어 고정
- **프라이머리 컬러**: 도메인 변수 (물리치료 = 블루 / 임대 = 그린) → 추후 테넌트별 브랜딩 확장 가능
- **플랫폼**: 모바일 퍼스트 (Capacitor), 하단 탭 네비게이션, 한 손 조작 기준 터치 타겟

### 7-1. 물리치료 모듈 (1순위)

#### 라벨 교체 (코어 재사용)

| 코어              | 물리치료 라벨  |

#### 전용 화면·기능 추가

| 화면/기능               | 명세                            | 코어 접점                            |
|---------------------|-------------------------------|----------------------------------|
| Journal(진료 일지) 특화 폼 | 신체 부위 칩(바디맵) → 증상 → 치료 내용 단계형 | C7 슬롯 + `journal_physio_details` |
| Schedule(예약) 캘린더    | **시간 슬롯 기반** 일/주 뷰            | C8 물리치료 분기 뷰                     |
| Consent(민감정보 동의) UI | 의료법 요건 문구, 철회 이력 표시           | C5 특화                            |
| 보관 만료 알림            | 진료 기록 10년 만료 90일 전 OWNER 알림   | C10 알림 확장                        |

#### 고유 제약 (법규)

- Journal 삭제 불가 (의료법 5~10년 보관) — UI에 삭제 버튼 미노출
- `ASSISTANT ↛ journal:read` — 화면/탭 미노출 방식 (코어 UI 정책 준수)
- AI 출력 가드레일: "소견", "진단" 등 감지 시 재생성/경고 문구

| **납부 현황 보드** | **월 단위 상태 그리드** (완납/연체/미납) — 캘린더 아님                | C8 임대 분기 뷰, `OVERDUE` 상태 활용                    |

#### 고유 판단

> **Schedule 뷰 분기가 필수인 이유**: 물리치료는 "시간 슬롯"(하루 안 시간대), 임대는 "월 단위 상태"(완납 여부)가 핵심 관심사. 단일 캘린더 UI로 통일 시 양쪽 모두 UX 붕괴 — 코어는 상태
> 모델만 공유, 뷰는 분기.

## 9. 진행 로드맵 (How)

```text
Phase 0  본 문서(v0.2) 확정 → 백엔드 용어 정렬
         └ Journal 유지 / Event→Schedule 리네이밍 / Role-Permission 매핑 도입

Phase 1  코어 디자인 (C3, C4, C6, C9)
         └ 도메인 라벨 없이 뉴트럴 톤으로 컴포넌트 확정 (Claude Design)

Phase 2  물리치료 스킨 + 전용 화면 2종
         └ 일지 특화 폼(C7 슬롯), 예약 캘린더(C8 분기)

Phase 3  임대 스킨 검증
         └ 세입자 상세(C4 재사용) + 납부 보드(C8 분기)
         └ ⚠ 코어 컴포넌트 재사용이 어색하면 코어 추상화 실패 신호 → Phase 1 회귀
         └ Engagement 엔티티 재도입 (계약 독립 모델링)

Phase 4  Auth 서버 분리
         └ RS256 + JWKS 전환 → aud 클레임 도입 → 블랙리스트 소유권 이관
         └ 계정(users)–멤버십(memberships) 분리

Phase 5  fintech-be 연결 (§5 체크리스트 수행 — Auth 무수정 검증)
```
