1. DRY 원칙 (Don't Repeat Yourself)

개념: "반복하지 말라"는 뜻입니다. 코드 내에 동일한 로직이 여러 번 나타나는 것을 피하는 원칙입니다.

적용: findById(...).orElseThrow(...)처럼 사용자를 조회하고 없으면 예외를 던지는 코드가 여러 메서드에 중복되었습니다. 이를 private findUserById(Long userId) 같은 헬퍼 메서드로 따로 뽑아내면, 코드가 간결해지고 나중에 수정할 일이 생겨도 그 헬퍼 메서드 하나만 고치면 됩니다.

2. 데이터 무결성 및 동시성 제어

개념: 동시에 여러 요청이 들어올 때 데이터가 꼬이거나 중복으로 생성되는 것을 막는 것입니다.

적용: createRelation 시, 1번 요청이 "존재 여부 확인" (없음) 후 "저장"을 하기 전에 2번 요청이 "존재 여부 확인" (없음)을 하면, 관계가 중복 생성될 수 있습니다.

DB 유니크 제약 (Unique Constraint): (manager_id, customer_id) 조합은 고유해야 한다고 DB 레벨에 제약(자물쇠)을 겁니다. 이게 가장 확실한 방어선입니다.

서비스 예외 처리: DB 제약조건에 걸리면 DataIntegrityViolationException이 발생합니다. 이를 try-catch로 잡아서 "이미 존재하는 관계입니다"(RELATION_ALREADY_EXISTS) 같은 명확한 예외로 변환해 사용자에게 알려줍니다.

3. JPA 엔티티 관리 일관성

개념: JPA(데이터베이스 기술)의 작동 방식(영속성 컨텍스트)에 맞게 코드를 작성하는 것입니다.

적용: deleteRelation 시, 단순히 deleteById(id)를 호출하기보다 findById(id)로 엔티티를 먼저 조회한 후, 그 엔티티 객체를 delete(entity)에 넘깁니다.

이유: 이렇게 하면 해당 엔티티가 JPA의 관리 하(영속성 컨텍스트)에 들어온 상태에서 삭제 로직이 실행됩니다. 특히 Soft Delete( @SQLDelete)처럼 일반 삭제가 아닌 특별한 로직이 적용된 경우, 이 방식이 JPA의 생명주기와 일관되게 동작하여 더 안정적입니다.

4. 관심사의 분리 (Separation of Concerns)

개념: 하나의 클래스나 메서드가 너무 많은 책임을 갖지 않도록 역할을 명확히 나누는 것입니다.

적용: 비즈니스 로직과 보안(인가) 로직을 분리합니다.

서비스 계층 (RelationServiceImpl): "무엇을" 하는지(비즈니스 로직)에만 집중합니다. (예: "매니저와 고객의 관계를 생성한다.")

컨트롤러 / 시큐리티 계층: "누가" 할 수 있는지(인가 로직)를 검증합니다. (예: "로그인한 사용자가 요청된 매니저 본인이 맞는가?")

이유: 이렇게 분리해야 서비스 코드는 순수하게 비즈니스 로직에만 집중할 수 있고, 보안 관련 로직은 컨트롤러나 @PreAuthorize 어노테이션 등에서 일관되게 처리할 수 있어 유지보수가 매우 쉬워집니다
