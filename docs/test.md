# 실무 테스트 전략 요약

### **🎯 1. 핵심 철학: "선택과 집중"**
모든 코드를 테스트하는 것은 비효율적이며 불가능합니다. **"비용-효율"**과 **"위험도"**를 기준으로 우선순위를 정합니다. **테스트 피라미드 (7:2:1 법칙)**를 따르는 것이 가장 효율적입니다.

### **⚖️ 2. 테스트 피라미드 (범위별 전략)**

#### **🥇 1순위: 단위 테스트 (Unit Test) - 70~80%**
- **목적:** 가장 작은 단위(메소드/클래스)의 **'비즈니스 로직'**을 검증합니다.
- **특징:**
    - **Mock(목업)**을 사용해 의존성을 완벽히 '고립'시킵니다.
    - DB나 외부 API에 절대 의존하지 않습니다.
    - 속도가 가장 빠르고, 가장 많이 작성해야 합니다.
- **주요 대상:** Service 로직의 모든 분기문(if/else), 예외 처리, 계산/검증 로직.

#### **🥈 2순위: 통합 테스트 (Integration Test) - 15~20%**
- **목적:** 여러 단위가 '연동'될 때의 문제점을 검증합니다.
- **특징:**
    - 실제 (테스트용) DB나 환경을 사용합니다. (예: H2, Testcontainers)
    - Mock으로는 불가능한 영역을 검증합니다.
    - 단위 테스트보다 느립니다.
- **주요 대상:**
    - DB 트랜잭션
    - 동시성 제어 (Pessimistic/Optimistic Lock) -> **(지금 우리가 한 것)**
    - JPA 쿼리(@Query) 검증
    - 외부 API 실제 호출 검증

#### **🥉 3순위: E2E 테스트 (End-to-End Test) - 5% 미만**
- **목적:** 실제 사용자의 '핵심 시나리오'가 잘 동작하는지 검증합니다.
- **특징:**
    - API 호출부터 DB 저장까지 전 과정을 검증합니다.
    - 가장 느리고, 비용이 비싸며, 유지보수가 어렵습니다.
- **주요 대상:** "로그인 -> 주문 -> 결제"와 같이 절대 실패하면 안 되는 핵심 성공 시나리오 1~2개.
- **현실적 대안:** MockMvc를 사용한 컨트롤러 테스트로 E2E의 80% 효과를 대체할 수 있습니다.

### **💡 3. "CRUD는 어떻게 테스트하나요?" (실무 팁)**
테스트의 가성비는 **"단순함"**이 아니라 **"비즈니스 로직의 유무"**로 결정됩니다.

#### **1. "단순" CRUD (로직이 없는 경우)**
- **예시:** `service.findById(id)`가 `repository.findById(id)`를 그대로 호출만 하는 경우.
- **전략:** 단위 테스트의 가성비가 매우 낮습니다. (테스트를 위한 테스트가 됨)
- **권장:** 통합 테스트로 DB까지 연동해서 한 번에 검증하거나, 다른 테스트 시나리오에 묻어서 검증합니다.

#### **2. "복잡" CRUD (로직이 있는 경우)**
- **예시 1 (단위 테스트 대상):** 회원가입 시 이메일 중복 체크, 비밀번호 암호화 로직이 포함된 경우.
    - **-> Mock(목업)**을 사용한 단위 테스트가 필수입니다.
- **예시 2 (통합 테스트 대상):** 관계 생성 시 동시성 제어(Lock) 로직이 포함된 경우.
    - -> 실제 DB를 사용한 통합 테스트가 필수입니다.
