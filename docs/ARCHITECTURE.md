# 아키텍처 설계 원칙 (Architecture Design Principles)

이 문서는 Carelog 프로젝트의 백엔드 아키텍처를 설계하고 코드를 작성할 때 따르는 핵심 원칙을 정의합니다.

---

### 1. 기본 아키텍처 스탠스 (Architecture Stance)

- **OOP/DDD 원칙**: 엔티티는 데이터와 행위를 함께 캡슐화한다. 서비스는 여러 도메인 객체나 리포지토리를 엮어주는 오케스트레이션(흐름 조율)을 담당한다.
- **풍부한 도메인 모델 지향**: '빈약한 도메인 모델(Anemic Domain Model)'을 지양한다. 엔티티의 상태 변경은 엔티티가 스스로 수행하도록 메서드를 제공한다.

### 2. 핵심 패턴과 역할 (Key Patterns & Roles)

#### Entity vs. Mapper

- **엔티티 메서드**: **상태 변경의 주체**. 엔티티의 비즈니스 규칙을 스스로 검증하고 상태를 변경한다. (예: `updateNickname()`, `updatePassword()`)
- **매퍼(Mapper)**: 계층 간 **"데이터 변환"**을 전담하는 번역가. 비즈니스 규칙이나 검증 로직은 절대 포함하지 않는다.

#### Update 메서드 형태

- **권장**: 필드별 개별 `update` 메서드. (`updateNickname`, `updatePhone`)
    - 이유: 변경 의도가 명확하고, 부분 수정(PATCH)에 유연하게 대응할 수 있다.
- **비권장**: `updateUser(...)` 와 같이 한 번에 처리하는 포괄적인 메서드.
    - 이유: DTO 의존성 발생, 가독성 저하, 부분 수정 시 `null` 처리의 복잡성 등 문제가 발생한다.

### 3. 패턴 도입 전략 (Pattern Adoption Strategy)

#### Mapper 도입 시점

- DTO와 Entity 간의 변환 로직이 단순한 필드 매칭을 넘어서 복잡해질 때
- 변환 로직이 여러 서비스에서 중복해서 나타날 때
- 다양한 DTO가 생겨 변환 로직을 체계적으로 관리할 필요가 있을 때
- *단순한 CRUD 수준에서는 필수가 아님.*

#### UseCase 도입 시점

- 하나의 서비스 클래스가 너무 많은 책임(예: 표준 가입, 임시 가입)을 가져 비대해질 때
- 특정 기능의 비즈니스 흐름이 여러 외부 시스템 연동(결제, 알림 등)을 포함하여 복잡할 때
- **흐름:** `Controller` → `UseCase`/`Service` → `Mapper` → `Repository` 순으로 책임 분리

#### 권장 성장 경로

1.  **초기 단계**: 서비스에서 빌더 패턴 등을 사용해 엔티티를 직접 생성한다. 간단한 매핑은 서비스 내 private 메서드로 처리한다.
2.  **흐름 복잡도 증가 시**: 기능별 `UseCase`를 도입하여 서비스의 책임을 분리한다. (예: `StandardSignUpUseCase`, `TemporarySignUpUseCase`)
3.  **변환 복잡도 증가 시**: `Mapper` 클래스를 도입하여 데이터 변환 책임을 분리한다. 필요 시 `MapStruct` 같은 라이브러리 사용을 검토한다.

### 4. 요약 결론

> **상태 변경은 엔티티, 데이터 변환은 매퍼, 흐름 조율은 서비스/UseCase.**

> **단순할 땐 매퍼 없이도 괜찮다. 복잡해지면 UseCase → Mapper 순으로 점진적으로 도입한다.**

### 5. 데이터 모델링 전략 (V1/MVP)

V1/MVP의 빠른 개발과 V2로의 유연한 확장을 모두 고려하여 다음과 같은 데이터 모델링 전략을 채택합니다.

#### 5.1. 사용자 정보 모델링: 조인 테이블 전략 (Joined Table Strategy)

사용자(`User`)는 역할(`UserRole`)에 따라 `MANAGER`와 `CUSTOMER`로 나뉩니다. 각 역할에 특화된 데이터는 별도의 프로필 테이블에서 관리하여 `User` 테이블의 비대화를 방지하고 역할을 명확히 분리합니다.

- **`users`**: 모든 사용자의 핵심 공통 정보 (로그인 정보, 이름, `UserRole` 등)
- **`manager_profiles`**: `MANAGER` 역할의 사용자를 위한 추가 정보 (예: 사업자 정보, 특정 자격증 번호)
- **`customer_profiles`**: `CUSTOMER` 역할의 사용자를 위한 추가 정보 (예: 개인 동의 항목, 특이사항)

`User` 엔티티는 `ManagerProfile`, `CustomerProfile`과 `OneToOne` 관계를 맺습니다.

**기대 효과:**
- **V1 개발 속도:** V1에 필요한 `MANAGER` 타입(예: 도수치료사)을 위한 필드만 `manager_profiles`에 추가하여 신속하게 개발합니다.
- **V2 확장성:** V2에서 새로운 `MANAGER` 타입이 추가될 경우, `manager_profiles` 테이블에 컬럼을 추가하거나 별도의 상세 테이블을 추가하는 등 유연하게 대응할 수 있습니다.

#### 5.2. 비즈니스 데이터 모델링: 별도 도메인 테이블 전략 (Separate Domain Table Strategy)

`MANAGER`가 `CUSTOMER`를 위해 기록하는 데이터(예: 치료 일지, 상담 기록)는 **독립된 도메인 테이블**로 분리하여 설계합니다.

- **예시:** `therapy_logs` 테이블
  - `id`, `manager_id`, `customer_id`, `치료 내용`, `방문 일시` 등
  - '도수 치료'라는 특정 비즈니스 도메인에 종속적인 데이터를 관리합니다.

**기대 효과:**
- **도메인 간 독립성:** V2에서 '미용'이나 '법률 상담' 같은 새로운 서비스가 추가되더라도, `beauty_logs`, `legal_consulting_logs` 등 신규 테이블만 추가하면 됩니다. 기존 `therapy_logs` 테이블이나 로직에 전혀 영향을 주지 않아 안전하고 독립적인 확장이 가능합니다.
